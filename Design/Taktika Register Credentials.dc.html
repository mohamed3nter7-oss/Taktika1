Create account

Email, password, one Google path. Nothing is submitted here — the screen validates locally and advances, and the account is created at the end of screen 2. The two options differ in where the Google path sits and in how the screen tells you it is one of three.

Recommendation

Take 1a: one centred 440px card, Google above the email fields, a three-segment bar with a "Step 1 of 3" label. Google goes above because the whole point of that path is skipping password creation, so it has to be offered before the password and its checklist have been read — and on the mid-range Android hardware that dominates this market the user is usually already signed into a Google account, which makes it one tap against roughly forty keystrokes. Email users pay one beat of scanning for it, which costs nothing, because a user who arrived intending to type is already committed. The segment bar beats a named stepper: naming three stages on screen 1 promises specific content the user cannot yet judge, and it consumes the vertical space the password checklist needs when it opens. 1b's persistent named rail is the honest alternative if abandonment turns out to be about length rather than friction, but it fixes the layout at two columns and has nothing to say below 1024px.

Reveal toggle, no new primitive

Input has an iconStart slot and no trailing slot, so rather than overlay an IconButton on the field's internals the toggle sits on the label row as a link Button — "Show" / "Hide", inline-end, with aria-label and aria-pressed and the system's standard 2px focus ring. Text rather than an eye glyph: it localises cleanly (إظهار / إخفاء) and states the action instead of implying it. If you would rather have it inside the field, that is the one primitive change to make — a trailing action slot on Input — and it is a change, not an invention.

The checklist is placeholder content

Four rules, dashed border, marked in the block itself: the real ones come from the backend DTO and no policy was invented here. It appears on focus and rules resolve individually, so the user is told which requirement is outstanding rather than being given a colour. The rows carry no red in the error state — the unmet rules are already visibly unmet, and the failure is reported once, at the field.

The Google mark is a reserved slot

A 20px dashed square holds the space and nothing is drawn in it. Google's branding guidelines govern the mark's size, its clear space, and which button backgrounds and borders are permitted, so the button's surface may have to change at implementation — the secondary variant shown here is the system's closest legal starting point, not a promise. The divider reads "or", lowercase.

Neither state 5 nor state 7 is an error

Both sit on the sunken surface with a strong hairline and no semantic colour at all — no danger tint, no red text, no icon of alarm. State 5 leads with a route: log in with that email, prefilled. State 7 explains the collision in one sentence and asks for the existing password once, which is the whole of the linking transaction; it replaces the form rather than sitting above it, because the email is already settled and re-offering the field would invite a second guess.
